# Operator (computer use on a legacy system): agent notes

Read this before you change `src/features/operator/`, `/demos/operator`, `/api/operator/*`, `public/operator/` or `e2e/operator.spec.ts`. The rules for every demo are in the root `AGENTS.md`.

- A live demo at `/demos/operator` in four places (Run, Rules, Under the hood, Connect a client; `?tab=`, `?run=`, `?replay=`): one agent, the Operator, keys HARBOURMASTER (the green-screen manifest and berth system of the fictional Port Authority of Meridia) by looking at pictures of the Screen and using the keyboard and mouse. Domain language: `src/features/operator/GLOSSARY.md`. Decisions: `docs/adr/0025-the-operator-keys-through-a-guard.md`, `docs/adr/0026-the-legacy-system-is-a-state-machine-in-the-sandbox.md`.
- HARBOURMASTER is a pure state machine in `src/features/operator/legacy/` (`boot`, `step`, `render`): no I/O, no clock, no zod. It runs in the Run's Screen sandbox, in the visitor's browser ("take the keyboard") and in the server's replay of a hand attempt. After changing it, `domain/guard.ts`, `domain/rule-kinds.ts`, `domain/iso6346.ts` or `server/sandbox/`, run `pnpm build:operator-screen` (a test fails on a stale bundle).
- Every Action, whoever drives, goes through `performAction` in `server/act.ts`: the workflow's step for the Operator and the `screen_*` MCP tools for an outside client. Never add a way to change the Books that does not pass the Guard. A new capability is an MCP tool (`domain/mcp-tools.ts` lists them; `server/mcp.ts` registers them).
- Rules are data (`domain/rules.ts`, versions in `operator.rulebooks`); the Guard (`domain/guard.ts`, before a key) and the checks (`domain/checks.ts`, after the Run) are code, and only they refuse, pause or return a Finding. A new Rule needs both a Guard or check and a test that it can fail. The model never approves: a pause is a workflow hook a person settles, and `decide_approval` is refused for a Run the caller drives.
- The workflow is `operatorRun` in `server/run-workflow.ts`; its step names are replay keys. That file may import only pure modules at runtime (`server/counters.ts`, `domain/limits.ts`): anything that reaches Postgres or the sandbox goes in `server/run-steps.ts`.
- Caps are `LIMITS` in `domain/limits.ts`, taken in `server/runs.ts` and `server/act.ts`. Two sandboxes per Run, both with no network: the Screen sandbox (forked from the base `operator-screen-base-v1`, built on first use) and the Code sandbox for `run_code`, which must stay a separate microVM.
- Env: `DATABASE_URL`, optional `OPERATOR_AI_GATEWAY_API_KEY` (falls back to `DOCUMENT_COMPLIANCE_AI_GATEWAY_API_KEY`), `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `RATE_LIMIT_SALT` (also signs MCP tokens), `E2E_BYPASS_TOKEN`; Vercel Sandbox authenticates with OIDC as for Sieve. Data lives in the `operator` schema and the private `operator` bucket (`supabase/migrations/20261119130000_operator.sql` and `20261119130100_operator_client_busy.sql`, added with `git add -f`; apply both before deploying).
- Sandboxes must not leave snapshots behind (ADR 0026): only the Screen base is persistent, with one snapshot that expires (`BASE_OPTIONS` in `server/screen.ts`, never `snapshotExpiration: 0`); every other Sandbox is `persistent: false`, said again with `update` after `fork`/`getOrCreate`; every delete passes `deleteOrphanSnapshots: true`. `sandbox-snapshots.test.ts` pins it.
- Samples: three Tasks in `domain/tasks.ts`, each with a Fixture, Expectations and a Script a test plays to a correct result; Manifests in `public/operator/samples/`. The recorded Run in `public/operator/replays/` is made with `pnpm record:operator-replay <runId>` from a correct Run of the `e2e` Owner.
- Tests: `e2e/operator.spec.ts` is skipped unless `E2E_OPERATOR=1`. The Operator is stubbed (`x-operator-stub` carrying the e2e bypass token plays the Script, no model spend) but every Run still starts real sandboxes and writes to the `e2e` Owner. `E2E_OPERATOR_LIVE=1` adds one Run on the real model (about $0.40). Run it only when asked, like the rest of the suite.
