# Operator (computer use on a legacy system): agent notes

Read this before you change `src/features/operator/`, `/demos/operator`, `/api/operator/*`, `public/operator/` or `e2e/operator.spec.ts`. The rules for every demo are in the root `AGENTS.md`.

- A live demo at `/demos/operator` in four places (Run, Rules, Under the hood, Connect a client; `?tab=`, `?run=`, `?replay=`): one agent, the Operator, keys HARBOURMASTER (the green-screen manifest and berth system of the fictional Port Authority of Meridia) by looking at pictures of the Screen and using the keyboard and mouse. Domain language: `src/features/operator/GLOSSARY.md`. Decisions: `docs/adr/0025-the-operator-keys-through-a-guard.md`, `docs/adr/0026-the-legacy-system-is-a-state-machine-in-the-sandbox.md`.
- HARBOURMASTER is a pure state machine in `src/features/operator/legacy/` (`boot`, `step`, `render`): no I/O, no clock, no zod. It runs in the Run's Screen sandbox, in the visitor's browser ("take the keyboard") and in the server's replay of a hand attempt. The Guard in front of it is `server/sandbox/screen-core.ts`, which both the Screen sandbox's process (`screen-entry.ts`) and the stubbed Screen (`stub-screen.ts`) run. After changing `legacy/`, `domain/guard.ts`, `domain/rule-kinds.ts`, `domain/iso6346.ts` or `server/sandbox/`, run `pnpm build:operator-screen` (a test fails on a stale bundle).
- Layers (`docs/engineering/architecture.md`): services in `server/services/` (`runs`, `steps`, `rulebooks`, `manifests`, `clients`, composed in `index.ts` as `OperatorServices`), ports in `server/ports.ts`, adapters wired in `server/container.ts` (`operator`) and `server/steps-container.ts` (`runSteps`, kept apart so the workflow's steps never import the routes or the MCP server). The adapters: `server/adapters.ts` over the SQL in `server/repository.ts` (its own pool in `server/db.ts`, which keeps `timestamptz` as `Date`), `server/storage.ts` (Frames, Manifest files), `server/screen.ts` and `server/code-sandbox.ts` (Vercel Sandbox), `server/operator.ts` (`modelOperator`, `scriptedOperator`). Errors are the platform's; `server/errors.ts` holds only `ScreenUnavailable` (409).
- REST (`server/api.ts`, `operatorApi`: same-origin writes, the gate and the Owner, the visitor, the services): `GET|POST /api/operator/runs` (POST starts a Run the Operator keys, `driver: "operator"`, or files a hand attempt, `driver: "hand"`; both answer `{ runId }`), `GET /api/operator/runs/[runId]`, `POST /api/operator/runs/[runId]/stop`, `PATCH /api/operator/runs/[runId]/approvals/[approvalId]` (`{ decision }`), `GET /api/operator/runs/[runId]/events` (NDJSON, `?after=`), `GET /api/operator/runs/[runId]/frames/[n]` (PNG), `GET|POST /api/operator/rulebooks`, `GET|POST /api/operator/manifests` (POST opens an upload), `POST /api/operator/manifests/[manifestId]/read`, `POST /api/operator/tokens` (an MCP token). No server actions. The browser reaches them only through `components/api.ts`.
- Every Action, whoever drives, goes through `performAction` in the `steps` service: the workflow's step for the Operator and the `screen_*` MCP tools (through the `runs` service's `clientCall`) for an outside client. Never add a way to change the Books that does not pass the Guard. A new capability is an MCP tool (`domain/mcp-tools.ts` lists them; `server/mcp.ts` registers them, calling the same services as the routes on `operator(mode)`, so an e2e request over MCP is stubbed too).
- Rules are data (`domain/rules.ts`, versions in `operator.rulebooks`); the Guard (`domain/guard.ts`, before a key) and the checks (`domain/checks.ts`, after the Run) are code, and only they refuse, pause or return a Finding. A new Rule needs both a Guard or check and a test that it can fail. The model never approves: a pause is a workflow hook a person settles, and `decide_approval` is refused for a Run the caller drives.
- The workflow is `operatorRun` in `server/run-workflow.ts`; its step names (and the file) are replay keys. That file may import only pure modules at runtime (`server/counters.ts`, `domain/limits.ts`): its steps call `server/run-steps.ts`, which hands each to the `steps` service of the Run's own mode (`ctx.stubbed`).
- Caps are `LIMITS` in `domain/limits.ts`, taken in the `runs` service (Runs per visitor, per Owner, one live Screen, hand attempts) and the `steps` service (Actions, code runs) before the Screen, the Code sandbox or the model is reached. Two sandboxes per Run, both with no network: the Screen sandbox (forked from the base `operator-screen-base-v1`, built on first use) and the Code sandbox for `run_code`, which must stay a separate microVM.
- Env: `DATABASE_URL`, optional `OPERATOR_AI_GATEWAY_API_KEY` (falls back to `DOCUMENT_COMPLIANCE_AI_GATEWAY_API_KEY`), `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `RATE_LIMIT_SALT` (also signs MCP tokens), `E2E_BYPASS_TOKEN`; Vercel Sandbox authenticates with OIDC as for Sieve. Data lives in the `operator` schema and the private `operator` bucket (`supabase/migrations/20261119130000_operator.sql` and `20261119130100_operator_client_busy.sql`, added with `git add -f`; apply both before deploying).
- Sandboxes must not leave snapshots behind (ADR 0026): only the Screen base is persistent, with one snapshot that expires (`BASE_OPTIONS` in `server/screen.ts`, never `snapshotExpiration: 0`); every other Sandbox is `persistent: false`, said again with `update` after `fork`/`getOrCreate`; every delete passes `deleteOrphanSnapshots: true`. `sandbox-snapshots.test.ts` pins it.
- Samples: three Tasks in `domain/tasks.ts`, each with a Fixture, Expectations and a Script a test plays to a correct result; Manifests in `public/operator/samples/`. The recorded Run in `public/operator/replays/` is made with `pnpm record:operator-replay <runId>` from a correct live Run of the `e2e` Owner (a stubbed Run's Frames are placeholders, and the script refuses one).
- Stubbing: an e2e request without `x-e2e-live: 1` gets `operator({ stub: true })`, and every Run it starts is marked `stubbed` on its row and its context, so the workflow's steps and later MCP calls get the same: the scripted Operator (the sample Task's Script; an own Task finishes at once), the stubbed Screen (`server/sandbox/stub-screen.ts`: HARBOURMASTER and the Guard in the server's own process, kept on `globalThis` by run id, each Action split into the same inputs the sandbox's driver sends, a placeholder picture), and a Code sandbox that answers it did not run. The workflow, the gates, the caps, the Guard, the checks, Storage and the `operator` schema stay real. The stubbed Screen lives in one process, so the stubbed suite needs the app it tests in one process (`next dev` or `next start`, as Playwright runs it), not a deployment.
- Tests: `server/services/services.test.ts` (who may decide an Approval, an expired one refused, one client call at a time, paused time off the clock, caps before the work, Storage paths, tokens die with the pass, a sample Script through the stubbed Screen to a Correct Verdict and a refused Screen), the Guard and checks in `domain/`, HARBOURMASTER's traps in `legacy/`, `sandbox-snapshots.test.ts` and `screen-bundle.test.ts`. `e2e/operator.spec.ts` is skipped unless `E2E_OPERATOR=1` and runs stubbed (no Sandbox, no model; rows under the `e2e` Owner). `E2E_OPERATOR_LIVE=1` adds one Run on the real model and a real Screen sandbox (`x-e2e-live`, about $0.40). Run it only when asked, like the rest of the suite.
