# Harness (Jod: Harness for Bank): agent notes

Read this before you change `src/features/harness/`, `/demos/harness`, `/api/harness/*`, `fixtures/harness/` or `e2e/harness.spec.ts`. The rules for every demo are in the root `AGENTS.md`.

## The demo

- A live demo at `/demos/harness` in six tabs (Chat, Pipelines, Knowledge, Skills, Audit, Docs) plus Demo mode: a chat Agent set up for the Pensions Operations Desk of the fictional Harbour Bank & Trust. Tabs are addressable: `?tab=`, `?session=`, `?run=`. It opens with the shared `DemoBar` (`rowFrom="xl"`, one row only from 1280px): the six places are its view tabs (ids `harness-tab-<tab>`, panels `harness-panel-<tab>`, which Demo mode's focus ring in `harness.css` keys on), and Connect Claude, Demo mode and the Staff switcher sit on its right. The Connect and consent pages use `HarnessPageBar` (`components/harness-bar.tsx`), the same bar with the places as links.
- Domain language: `src/features/harness/GLOSSARY.md`. Read it before naming anything in `src/features/harness/`: a Session is not a Thread, a Step is not a Job, a Staff member is not a Member. Decisions: `docs/adr/0013-harness-one-mcp-server-for-chat-and-claude.md` to `docs/adr/0018-audit-events-are-append-only.md`, and `docs/adr/0022-sandbox-on-vercel-sandbox.md` (which supersedes 0017).

## Boundaries

- The Agent reaches everything through the Harness MCP server (`/api/harness/mcp`). A new capability is a new MCP tool, never a chat-only tool; the only chat-local tools are `load_skill` and web search. No tool gives an Approval.
- Outside clients sign in with OAuth (`domain/oauth.ts`, consent at `/demos/harness/mcp/authorize`) or paste a token. Every Harness token (OAuth, pasted, chat) carries `iat` and is refused once its Owner pressed "Disconnect all MCP clients" on `/access/profile`; a code is redeemed once; the consent page warns and needs "I trust <host>" ticked for a callback that is neither loopback nor a known client's, and the consent action redirects nobody without Access. Shared with the Client Manager: `docs/engineering/access.md`, "MCP tokens".
- The layers are `docs/engineering/architecture.md`'s. Services (`server/services/<area>.ts`: staff, sessions, chat, runs, rules, skills, knowledge, records, audit, sandbox, connect, and the page's `firstView`) hold every rule; ports (`server/ports.ts`) are the repositories (the SQL modules: `sessions.ts`, `rules.ts`, `skills.ts`, `records.ts`, `audit.ts`, `pipelines/store.ts`, `knowledge/repository.ts`, `workspace.ts`), the model, Storage, Vercel Sandbox and the Workflow SDK; `server/container.ts` (`harness(mode)`) wires them. A write and its Audit event that must stand or fall together share a transaction in the repository, with the event built by the service (a `plan`/`decide` callback runs under the row lock when the rule needs the locked row, as the four-eyes check does).
- REST: every route under `src/app/api/harness/` is a `.handle()` on `harnessApi` (`server/api.ts`: `sameOrigin`, `withOwner`, `withVisitor`, `withServices(harness)`, `withStaff`) with its `params`/`query`/`body` schema. `withStaff()` seeds the Owner's Workspace on first use and adds `staff`, `everyone` and `caller` (`{ access, owner, staff, visitor }`); the `harness_staff` cookie only remembers which of the Owner's own Staff is active and counts only if it names one of them. Pages use `signedIn()` (`server/page.ts`), the same service. The bearer routes (`/mcp`, `/oauth/register`, `/oauth/token`) check their own token. The consent page posts its Allow or Deny to `POST /api/harness/consents`, which answers where to send the browser.
- Roles are decided in one place: `can(staff, action)` in `domain/permissions.ts`; `refusalFor()` there words the 403 with the Role needed. A route stacks `authorize(permits(action))`; a service checks again with `assertCan()` (`server/errors.ts`), and an MCP tool applies the same `refusalFor` to the token's Staff member, so a future RBAC rule is one more policy. High-risk Approvals need an admin who did not start the Run (`approvalRefusal`, in the Runs service, against the locked Approval row). Anyone in a Workspace may switch Staff, so a Role is not a security boundary between visitors; Access and the Owner are.
- Every write is audited by its service (`AuditLog.record` after the fact, `strict` before work that must not happen untraced, or the repository's `auditIn(tx, …)` inside the write's transaction), with an action from the fixed list in `domain/audit.ts`. Details hold ids, names and sizes, never a secret or a whole document. `harness.audit_events` refuses UPDATE and DELETE; events go only when the Workspace does.
- The HTTP contract is `domain/api.ts` (paths, request and response types, the `ROUTES` table). The browser calls it only through `components/api.ts` (typed wrappers over `@/platform/client/api`; a refusal is an `ApiError`, a refused Rule edit's fields come from `ruleErrorsOf`). Errors are the platform's (`@/platform/errors`); `RuleRefusedError` carries `errors` in the 400. Tabs build from `components/ui.tsx` (the Colonnade primitives: `Panel`, `Button`, `Badge`, `inputClass`, `segmentClass` for a row of pressed choices) and read `useHarness()`; Demo mode drives them through the controller registry (`useController`), never through a component's internals.
- Rules are data, checks are code (ADR 0015): Defaults in `domain/rules/defaults.ts`, edits as Versions in `harness.rule_versions`, checks as pure functions in `domain/pipelines/`. Only code returns a Finding. Skills are `SKILL.md` text; a Rulebook's body is rendered from its Rules.
- Caps live in `LIMITS` in `domain/limits.ts`; the hourly ones are `pgRateLimiter` caps on `harness.rate_hits` (`server/container.ts`), taken in the service before the paid step, so the app, the chat and MCP are held the same way.
- The Run engine (`run-workflow.ts`, `run-steps.ts`, `pipelines/*`) runs in the Workflow SDK, outside any request: its function and file names are replay keys. It carries its stub flag in the Run's context (`stubbed`), set from the container when the Run starts.

## Attachments and Sources

- A file attached in chat is a pending Source ("attached, not filed", ADR 0016): `api.sources.attach` uploads it and stops, so it has no Passages and no Conflict check. The Agent reads it (`read_source` returns its text) and a Pipeline takes it (`sourceTexts.read` in `server/knowledge/text.ts`); `list_sources` and search never return it; `list_attachments` and the "Attached in this Session" list in the Agent's instructions (built each turn from the database, `sessionRepository.attachments`) do. Tools that take a Source id also accept a file name or title of one of the caller's Session's attachments, resolved only on a single match (`resolveSourceRef` in `domain/attachments.ts`); without a Session (an outside MCP client) only ids work. A Source's Preview (`GET /api/harness/sources/[id]/preview`) returns its raw text and a 5-minute signed link to its file, audited as `source.read`. It is filed only by the Agent's `file_source` or a person's File button in the Knowledge tab, which is also the only place a file is uploaded and read in one go.
- Removing a Source is soft (the Knowledge service's `remove` sets `harness.sources.deleted_at`). Every query on Sources, Passages and Conflicts filters removed Sources out, `harness.search_passages` included; a new read of `harness.sources` must do the same. its `sweep` deletes the row and its file 30 days later, whenever the Owner adds or removes a Source; the `harness-purge-removed-sources` cron deletes removed Sources that have no file.

## Data and env

- Data lives in the `harness` schema and the private `harness` bucket (created by the first migration). Apply five migrations, in this order: `supabase/migrations/20261117120000_harness.sql` (needs the `vector` extension), `20261117130000_harness_pipelines.sql`, `20261117150000_harness_knowledge.sql`, `20261117160000_harness_search_rate.sql`, `20261127110001_harness_source_soft_delete.sql`. The migrations and `public/harness/samples/*` are added with `git add -f` because of a global gitignore. Every table carries `owner` and cascades from `harness.workspaces`, the only Harness table in `access.owned_tables`; never register another, or the Owner purge fails on the Audit trail.
- Env: `DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `RATE_LIMIT_SALT` (shared; it also signs every Harness token, so rotating it revokes them), and `JOD_BANKING_HARNESS_AI_GATEWAY_API_KEY` (falls back to `DOCUMENT_COMPLIANCE_AI_GATEWAY_API_KEY`). Optional: `HARNESS_MODEL`, `HARNESS_STEP_MODEL`, `HARNESS_EMBEDDING_MODEL`, `E2E_BYPASS_TOKEN`. The Sandbox is Vercel Sandbox and authenticates like Sieve's: OIDC on Vercel, `VERCEL_OIDC_TOKEN` from `vercel env pull` locally; without either it answers "Sandbox unavailable".
- Sample data: `node --experimental-strip-types scripts/build-harness-samples.mts` writes the sample Schedules and remittance advice, and `scripts/build-harness-knowledge.mts` the seed Knowledge Sources (`seed-texts.ts`, from `fixtures/harness/knowledge/`) and the sample Circular and fee workbook, under `public/harness/samples/`. Re-run them after changing the sample book or the knowledge fixtures.
- `20261128100300_harness_rest_indexes.sql` adds the rate limiter's `(kind, created_at)` index and a partial index for the stale-read sweep; additive.
- Tests: `e2e/harness.spec.ts` is skipped unless `E2E_HARNESS=1` and needs the migrations applied to the project it runs against. It runs stubbed by default (the e2e token alone): the container's stub adapters are the canned Agent (`stubAgent` in `server/chat.ts`, which calls one MCP tool in process), Runs whose model Steps use their fallbacks, the Conflict check's `stubVerdicts`, no embeddings (`noEmbedder`) and an in-memory Sandbox (`stubSandboxes`). Gates, caps, the database, Storage and the Workflow SDK stay real; it writes to the `e2e` Workspace and uploads a sample to Storage. `E2E_LIVE=1` reaches the models (paid). Run it only when the user asks, like the rest of the suite. Unit tests are the services' invariants with fake ports (`server/services/*.test.ts`), the Rule checks and the token checks.

## Sandbox and Demo mode

- The Sandbox is for the Agent to code with (ADR 0022): Vercel Sandbox with no network, one per Session (`harness-session-<id>`, the `code_` MCP tools) and one per reading-Step model call (`run_code` in `server/pipelines/code.ts`, removed when the call ends). Every Role may use it; it is held in by `SANDBOX_LIMITS` (`domain/sandbox.ts`), the hourly `sandboxCommandsPerHour` cap and the Audit trail (the Sandbox service audits every command before it runs; `stubSandboxes` stands in for the e2e suite). Code is analysis: only a Pipeline's checks return a Finding. Do not add example prompts or Demo mode Beats that ask for the Sandbox; the Agent decides when to code.
- Demo mode opens only from the bar's Demo mode button, never by itself (a dismissible "Continue where you left off" hint may be offered). Its six Scenarios are data in `components/demo-mode/scenarios.ts`; a Beat that needs a tab's controller opens that tab first, because a tab mounts when it is first visited.
