# Bank (Tidewater Bank): agent notes

Read this before you change `src/features/bank/`, `/demos/bank`, `/api/bank/*`, `fixtures/bank/`, `e2e/bank.spec.ts`, the Growth routines in `docs/routines/` or the growth guard. The rules for every demo are in the root `AGENTS.md`. A Bank Growth pull request may not change this file (it is outside the allowlist in `domain/growth.ts`).

## The demo

- A live demo at `/demos/bank`: a whole retail bank (fictional Tidewater Bank of Meridia, Meridian florin, play money) on a double-entry ledger, run from the app or by asking the Teller, that grows itself through GitHub. Tabs (`?tab=`): Bank (the Customer view), Teller (chat), Operations, Growth, Rules, Audit, Under the hood, Connect a client. Domain language: `src/features/bank/GLOSSARY.md` (a Staff member is not a Customer; a Confirmation is not an Approval; the Teller is the agent, `teller` is a Role). Decisions: `docs/adr/0023-bank-ledger-is-enforced-by-the-database.md`, `docs/adr/0024-the-bank-grows-itself-through-github.md`, `docs/adr/0033-bank-pull-requests-are-merged-by-a-routine.md`.

## Money and commands

- Money moves only through `bank.post_entry` (`post()` in `core/ledger.ts`): integer minor units, a balanced entry, the accounts locked first. Never write to `bank.postings`, `bank.journal_entries` or `bank.account_balances` directly; the database refuses UPDATE and DELETE on entries, postings and `bank.audit_events`. After changing the migration or a handler run `pnpm test:bank-db` (Docker: a throwaway Postgres; not part of CI).
- Everything the bank can do is a command in `domain/commands.ts`, run by `core/engine.ts` (validation, Role, idempotency key, Confirmation, Approval, handler, Audit event, outbox: one transaction). The app calls it through the command service (`server/services/commands.ts`): `GET /api/bank/read/<command>?input=<JSON>` for reads, `POST /api/bank/commands/<command>` with `{ input, idempotencyKey }` for writes; the MCP server (`/api/bank/mcp`) registers one tool per command from the same list and calls the same service. A new capability is a new command, never a route or a chat-only tool; `commands.test.ts` fails otherwise. `decide_approval` and `confirm_request` are never tools: no tool gives an Approval, and the Teller cannot confirm its own request.
- Layers (`docs/engineering/architecture.md`): `core/` is the domain and repository side (no Next imports; tested against Postgres directly) and is reached through the `CommandEngine` port. `server/services/` holds the services (`commands`, `staff`, `sessions`, `chat`) over the ports in `server/ports.ts`; `server/container.ts` wires the adapters (`sessions.ts`, `staff.ts`, `mcp-auth.ts`, `outbox.ts`, `growth.ts`, `chat.ts`, `sandbox.ts`); `server/api.ts` is the route stack `bankApi` (same origin, the Access gate and the Owner, the visitor, the services, then `withStaff`: the Owner's bank with its seed and the Staff member the `bank_staff` cookie names, checked against the Owner). Routes are thin `.handle()`s on it. Roles are decided only by `can(staff, action)` in `domain/permissions.ts`.
- The other endpoints: `PUT /api/bank/staff/active` (switch Staff, audited), `POST /api/bank/tokens` (an MCP token for Connect a client, audited), `GET|POST /api/bank/sessions`, `GET|DELETE /api/bank/sessions/[id]`, `POST /api/bank/sessions/[id]/chat` (NDJSON). `/api/bank/mcp` checks its own bearer and `/api/bank/github` GitHub's signature; neither is on `bankApi`. There are no server actions.
- Rules are data (`domain/rules.ts`, Versions in `bank.rule_versions`), checks are pure code (`domain/checks.ts`); every Parameter a check reads comes from the `Rulebook`. Caps are `LIMITS` in `domain/limits.ts`, taken in the services (`rate.take` on `pgRateLimiter` over `bank.rate_hits`, wired in `server/container.ts`): `write` before the engine runs, `message` before a Teller turn is saved, `sandbox` before each `run_code`. Refusals are the platform's errors (`core/errors.ts` re-exports them; a Rule's refusal answers 403, insufficient funds and a wrong state 409).
- Asynchronous work is a Vercel Workflow started from the transactional outbox (`enqueue()` in the command's transaction, `server/outbox.ts` dispatches, `server/workflows.ts` runs). Workflow and step function names are replay keys: do not rename or move them. The bank has a simulated clock per Owner (`bank.now(owner)`); `advance_clock` owes end-of-day (`core/day.ts`) for each date crossed.

## Growth

- `raise_request` → triage Workflow → GitHub issue (`bank:growth`) → the routine in `docs/routines/bank-growth.md` opens a pull request → the "PR Code + Security Review" routine reviews it on open and on every push and labels it `review:passed` or `review:changes` → the build session fixes what a `review:changes` review finds → the routine in `docs/routines/bank-merge.md` merges a pull request with `review:passed` at its newest head and green CI, or holds it (`bank:held`) for Reljod (`docs/adr/0033-bank-pull-requests-are-merged-by-a-routine.md`).
- `.github/workflows/bank-growth-guard.yml` fails a `bank:growth` pull request that leaves the allowlist; keep `scripts/bank-growth-guard.mjs` and `domain/growth.ts` identical (`growth.test.ts`).
- A visitor's words are untrusted everywhere in that loop: quoted, never followed. So is the spec the triage model writes from them: `issueBody` fences its Problem and Acceptance criteria as untrusted too.
- The Growth Rule (`growth.intake`) is per Owner and a Guest can edit it as supervisor, so its Default blocked topics (`GROWTH_BLOCKED_FLOOR` in `domain/rules.ts`) always apply: an Owner's words only add (`checkGrowthRequest` in `domain/checks.ts`, for the request and for the model's spec).
- With `--content` (the CI workflow and the merge routine) the guard also reads each file's patch and fails a diff that adds SQL naming a schema other than `bank`, removes an `owner =` / `owner:` predicate, or touches the environment (`contentFindings`, tested in `growth.test.ts`).

## Data, env and tests

- Env: `DATABASE_URL`, `RATE_LIMIT_SALT` (also signs bank MCP tokens), optional `BANK_AI_GATEWAY_API_KEY` (falls back to `DOCUMENT_COMPLIANCE_AI_GATEWAY_API_KEY`), `BANK_MODEL`, `BANK_TRIAGE_MODEL`; for Growth `BANK_GITHUB_TOKEN` (fine-grained: Issues read/write and Pull requests read on this repository only), optional `BANK_GITHUB_REPO`, `BANK_GITHUB_WEBHOOK_SECRET`. The Sandbox authenticates like Sieve's.
- Data lives in the `bank` schema (`supabase/migrations/20261119120000_bank.sql`, then `20261119121000_bank_growth_issue_filed_at.sql`, `20261127100000_bank_session_soft_delete.sql` and `20261128051700_bank_rest_indexes.sql`; added with `git add -f`), reached directly through the bank's own pool (`server/db.ts`: camelCase columns and its own type parsers, built once, counted by `DB_STATS=1`); `bank.banks` is in `access.owned_tables` and everything else cascades from it, except `bank.rate_hits` (no foreign key; registered on its own and pruned after a day by the `bank-delete-old-rate-hits` cron).
- Deleting a Teller conversation is soft (`bank.sessions.deleted_at`): every read of sessions and messages skips it, and the `bank-purge-deleted-sessions` cron deletes it with its messages 30 days later.
- Tests: `e2e/bank.spec.ts` is skipped unless `E2E_BANK=1` and needs the migration applied. The Teller turn is stubbed by the container: an e2e request without `x-e2e-live: 1` gets the canned Teller (`createStubTeller` in `server/chat.ts`: one real MCP tool call, no model) and no Sandbox; the engine, the database, the gates and the caps stay real. `E2E_BANK_LIVE=1` sends `x-e2e-live: 1` for one real turn. The e2e Owner's Growth requests are triaged without a model and never filed (keyed on the Owner, since a Workflow step has no request). (`BANK_GROWTH_E2E_LIVE=1` on a local server lifts that, to prove the loop by hand.) `src/features/bank/core/bank.smoke.test.ts` checks a running server (`BANK_SMOKE_URL`).
