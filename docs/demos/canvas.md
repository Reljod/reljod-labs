# Canvas (an analyst that answers with working interfaces): agent notes

Read this before you change `src/features/canvas/`, `/demos/canvas`, `/api/canvas/*`, `fixtures/canvas/` or `e2e/canvas.spec.ts`. The rules for every demo are in the root `AGENTS.md`.

- A live demo at `/demos/canvas` in five places (Ask, Data, Rules, Under the hood, Connect): one Analyst answers a Question about the open data of the fictional Republic of Meridia with Views. Domain language: `src/features/canvas/GLOSSARY.md`. Decisions: `docs/adr/0031-canvas-views-are-a-typed-grammar-drawn-by-one-mcp-app.md`, `docs/adr/0032-canvas-sandbox-image-and-the-local-runner.md`.
- A View is a spec in the View grammar (`domain/view.ts`, `canvas.view/1`), never model HTML. A new kind of chart is a change to the grammar, to `domain/chart-checks.ts` and to the App; `CHARTS` in `app/view-card.tsx` lists the kinds the App draws (others fall back to their rows).
- The App (`src/features/canvas/app/`, Preact, its own bridge) is one HTML document served as the MCP Apps resource `ui://canvas/view.html`. After changing anything under `app/`, run `pnpm build:canvas-app` and commit `view-app.generated.ts`. Nothing in `app/` may import zod or server code; it takes types only from `domain/`.
- Layers (`docs/engineering/architecture.md`): services in `server/services/` (`runs`, `views`, `conversations`, `rules`, `catalog`, `chat`, `connect`, `host`, composed in `index.ts` as `CanvasServices`), ports in `server/ports.ts`, adapters wired once in `server/container.ts` (`canvas`). The repositories are `server/{conversations,views,rules,trail,catalog,workspace}.ts`, on the shared `db()` pool; the Analyst's adapters are `server/analyst.ts` (model, scripted); the Sandbox's are `server/sandbox/session.ts` (`vercelSandbox`, with the local runner inside) and `server/sandbox/stub.ts`. Errors are the platform's; `server/errors.ts` holds only `RuleRefusal` and `RuleEditRefused` (400, with `rule` / `errors`) and `SandboxUnavailable` (409).
- REST (`server/api.ts`, `canvasApi`: same-origin writes, the gate and the Owner, the visitor, the services, the Caller with its Workspace made on first use): `POST /api/canvas/chat` (a Question, NDJSON), `GET /api/canvas/conversations`, `GET|DELETE /api/canvas/conversations/[id]`, `GET|POST /api/canvas/rules` (POST saves a Version and answers the Rules as they now are), `GET /api/canvas/trail`, `POST /api/canvas/tokens` (a pasted MCP token), `GET /api/canvas/app/frame`, `POST /api/canvas/app/call`. No server actions. The browser reaches them only through `components/api.ts`.
- The page is an MCP Apps host (`components/view-frame.tsx`, `server/services/host.ts`): the frame is `sandbox="allow-scripts"` and must never get `allow-same-origin`; the App's `tools/call` is proxied only for the tools in `APP_TOOLS`.
- The Analyst reaches everything through the Canvas MCP server (`server/mcp.ts`, `/api/canvas/mcp`, which checks its own bearer, then runs the tools on `canvas(mode)`). A new capability is a new MCP tool that calls a service method taking a `Caller`; the REST route calls the same method. The chat turn and the Host reach the server in process (`inProcess` in `container.ts`) with a short token from the `connect` service.
- Every Query goes through the `runs` service: the Run is taken from the allowance (and the Question's Sandbox seconds checked) before the Sandbox parses anything, then the Guard on the parsed statement (`domain/guard.ts`), the Trail, then the Sandbox. Never run SQL any other way. The Guard's fixtures (`domain/guard.fixtures.json`) are statements DuckDB really parsed; a new Guard rule needs a new fixture and a test that it can refuse.
- Rules are data (`domain/rules.ts`, Versions in `canvas.rulebooks`); the checks that read them are pure code (`guard.ts`, `verify.ts`, `chart-checks.ts`). Only `verify.ts` marks a View Verified.
- Deleting a Conversation is soft (`deleted_at`, filtered in every read in `server/conversations.ts` and `server/views.ts`), and takes its unpinned Views with it; the `canvas-purge-deleted` cron removes the rows after 30 days (`supabase/migrations/20261127140000_soft_deletes_and_caps.sql`).
- Every service write records a Trail event with an action from `domain/trail.ts`: `trail.record` (after the fact, best effort in production), `trail.strict` (before the work), or an event the repository writes in the write's own transaction (`trailIn`). `canvas.events` refuses UPDATE and DELETE; events go only when the Workspace does. Every table carries `owner` and cascades from `canvas.workspaces`, the only Canvas table in `access.owned_tables`.
- Data: generated from seeds in `domain/data/` (README in `fixtures/canvas/`); `pnpm render:canvas-data` rewrites the manifest and the two sample CSVs. Bump `DATA_VERSION` when a generated value changes and `RUNNER_VERSION` when the runner does: both key the Sandbox image.
- Env: `DATABASE_URL`, `CANVAS_AI_GATEWAY_API_KEY` (falls back to `DOCUMENT_COMPLIANCE_AI_GATEWAY_API_KEY`), optional `CANVAS_MODEL` (default `anthropic/claude-sonnet-5.5`); shares `RATE_LIMIT_SALT` (it signs Canvas MCP tokens) and `E2E_BYPASS_TOKEN`. The Sandbox authenticates like the Harness's. `CANVAS_LOCAL_RUNNER=<python with duckdb>` runs guarded Queries on the dev machine instead (never on Vercel or in production; it refuses `run_code`). Migrations: `supabase/migrations/20261119160000_canvas.sql`, `20261128134500_canvas_rest_indexes.sql` (the Trail by Conversation; added with `git add -f`).
- Stubbing: an e2e request without `x-e2e-live: 1` gets `canvas({ stub: true })`: the scripted Analyst (`stubPlan` in `domain/stub.ts`) and the canned Sandbox (`server/sandbox/stub.ts`), which parses from trees DuckDB 2.0.0 really produced (`server/sandbox/stub.fixtures.json`, written by `uv run --no-project --with duckdb==2.0.0 python scripts/canvas-stub-fixtures.py`) and computes the rows of the suite's few statements from the seeded generator. The Guard, the checks, the caps, the Trail and the database stay real. A token minted by stubbed services carries `stub` (only an e2e token may), so the MCP requests made with it, in process or over HTTP, run stubbed too. A new statement in the suite goes into the fixtures (`STUB_PROBES`) and gets a canned answer; `server/sandbox/stub.test.ts` fails until it does.
- Tests: `server/services/services.test.ts` (caps before the Sandbox and the model, Owner scope, the Analyst cannot save Rules, tokens die with the pass), `server/sandbox/stub.test.ts`, the Guard and checks in `domain/canvas.test.ts`. `e2e/canvas.spec.ts` is skipped unless `E2E_CANVAS=1` and runs stubbed; `E2E_CANVAS_LIVE=1` adds one Question to the real model and Sandbox (`x-e2e-live`). Run it only when asked.
- Not built yet (tables exist): Boards with a Refresh workflow, export, and bring-your-own CSV.
