# The Operator keys through a Guard, and only code says the work is right

Every bank, port, hospital and insurer has a system with no API: a green screen or a 2004 web app that people key data into all day. Operator shows one agent doing that keying by looking at the screen and using the keyboard and mouse. The usual way to build this is to give a computer-use model the screen and trust what it reports. That fails in two ways that matter in operations: the model can press a key it should not (release a hold, delete a line), and its own "done" says nothing about what the system actually stored.

We run **one agent, the Operator**, inside a harness that owns everything that decides. Words are in `src/features/operator/GLOSSARY.md`, types in `domain/contract.ts`.

- **The model sees a picture and sends Actions.** Each Turn it gets the Screen as a 1024 by 640 picture and answers with tool calls: `screen_click`, `screen_type`, `screen_key`, `screen_scroll`, `screen_wait`. It has no API to HARBOURMASTER and never sees the Books. Several Actions may go in one Turn (fill a form, press the key that saves), so a Run takes tens of model calls, not hundreds.
- **Our own tool set, not a provider's computer-use tool.** The AI Gateway model we use (`anthropic/claude-sonnet-5.5`, $2 in and $10 out per million tokens; a correct Run of the samples cost $0.24 to $0.40) is good at reading a screen and placing a click. Anthropic's native computer-use tool needs the provider's own SDK package and would give the in-app agent a tool surface an outside client does not have. With plain tools over pictures, any vision model works, and the Operator's tools are the MCP tools (below).
- **A Guard sees every keystroke before HARBOURMASTER does.** It runs the key on a copy of the machine, takes the difference (the Screen it would land on, the records it would change) and applies the Rules: allow, refuse, or pause. A real mainframe has no dry run; the production equivalent is a keymap per screen (screen code, key and field values to effect) over the terminal's buffer. Here the legacy system is ours, so the copy gives the same answer without a table to keep in step.
- **Rules are data; the Guard and the checks are code** (after ADR 0015). The Rulebook (which Screens, how many records a Run, which fields of an existing record are protected, which Actions need a person, the container check digit, sign-off, scope, Manifest match) is versioned per Owner; a Run snapshots the version it ran under. Three Screens (sign on, menu, timeout) can never be closed, or the Operator could not start or recover.
- **A guarded key pauses the workflow, not the model.** When the Guard answers pause, the workflow opens an Approval and waits on a hook (ten minutes, then the harness refuses it). The model is not asked and has no tool that approves. On approval the harness tells the Guard the fingerprint of exactly that change (kind, record, new values), good for one commit, and presses the key itself.
- **After the Run, code reads the Books and returns Findings.** The Books at the end are compared with the Task's Expectations (a sample Task), with the attached Manifest row by row, and with the Rules again on what was actually committed, including "every guarded change has a person's approval". The Verdict is `correct`, `incorrect` or `unverified` (an own Task with nothing to compare). The Operator's summary is kept as a note and decides nothing.
- **One MCP server, one path.** `/api/operator/mcp` exposes Runs, Frames, the Trail, the Rulebook and the `screen_*` tools. An outside client starts a Run with `driver: "client"` and drives the same sandboxed Screen through `performAction` (`server/act.ts`), the function the workflow's step calls, so the Guard, the caps and the Trail are the same. `decide_approval` exists for a Run the in-app Operator drives and is refused for a Run the caller drives: nobody approves their own key. This departs from ADR 0013 ("no tool gives an Approval") on purpose and only that far: the token is minted by the person, per Owner, and the caller is then acting as that person's console for someone else's keys.
- **Take the keyboard.** The same machine runs in the visitor's browser. The server trusts none of it: it replays the recorded inputs from the Task's Fixture and runs the same checks. A person passes no Guard, so the Rules show up as Findings.
- **The Trail is append-only.** Every Turn (model, tokens, cost), Action, Frame, Rule that fired, pause, decision, piece of code and Finding is an event ordered by `seq`; `operator.run_events` refuses UPDATE and DELETE (ADR 0018's rule, per Run).

## Consequences

- A new kind of Rule is code in `domain/guard.ts` and `domain/checks.ts` with a test that it can fail; a new value is a Rulebook edit.
- The Operator's context keeps the latest one to four pictures and replaces older ones with one line each, dropped in blocks of four so the provider's prompt cache holds (most of a Run's input tokens are cache reads).
- An Action is never retried by the workflow: a key pressed twice is a second key. A Turn (a model call) is. Opening and settling an Approval are never retried either.
- A client-driven Run has no workflow, so the harness does what the workflow would: one MCP call at a time (`client_busy_until`, a lease, so a dead call frees it), an Approval nobody decided before `expiresAt` is expired and refused on the next call or decision that touches the Run, and time spent paused for a person does not count against the Run's time cap.
- An Approval is for the values the person was shown: the Guard's fingerprint names the record and, for an add or an update, every value it would write. A different value for the same record pauses again.
- Caps live in `LIMITS` (`domain/limits.ts`) and are taken in `server/runs.ts` and `server/act.ts`, which the page, the workflow and the MCP tools all call.
- A scripted Operator (`x-operator-stub` with the e2e bypass token) plays a sample Task's Script instead of calling the model, through the same sandbox, Guard and checks. It cannot see a refusal, which the e2e suite uses to show the checks failing.
- The recorded Run under `public/operator/replays/` is served as static files outside the demo gate, like Sieve's: synthetic data, nothing to spend. Record only sample Tasks.
