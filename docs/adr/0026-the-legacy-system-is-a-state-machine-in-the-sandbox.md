# HARBOURMASTER is a pure state machine, shown by a browser inside the Run's sandbox

Operator (ADR 0025) needs a legacy system that is authentically awful, starts every Run from a known state, can be checked by code afterwards, and that a headless browser can show to a model without that browser reaching anything else.

- **The legacy system is a pure function.** `src/features/operator/legacy/` is HARBOURMASTER as `boot(fixture)`, `step(state, input, now)` and `render(state, now)`: plain JSON state, no I/O, no clock of its own. Its traps are real behaviour of that machine (a field that drops what does not fit, dates as DDMMYY, a confirm key, a record locked by another clerk, a session timeout), each proven by a test.
- **It is served inside the sandbox, not from the app.** A Run forks a Vercel Sandbox with a deny-all network policy. One Node process in it (`server/sandbox/screen-entry.ts`, bundled with esbuild into `screen-bundle.generated.ts`) is three things on loopback: HARBOURMASTER as a small web app, the Guard in front of it, and a driver that moves the mouse and presses keys in headless Chromium and answers with a PNG. We chose this over serving the legacy app from `/api/operator/legacy` with a network policy that allows only our origin: the sandbox then needs no route out at all, a local dev server works (a sandbox cannot reach `localhost`), and the state lives and dies with the Run.
- **The base is built once.** Chromium's headless shell and `playwright-core` are installed into a persistent sandbox named `operator-screen-base-v1` (about half a minute, with the network on), which is then stopped. Each Run forks it: the Screen is up in about ten seconds. If the base is missing, the first Run builds it; bump the name's suffix to change the image.
- **Only the base keeps a snapshot, and only one, for seven days.** A named Vercel Sandbox is persistent unless told otherwise, and a persistent one writes a snapshot of its whole disk (about 1 GB) every time it stops; those count against the team's quota until they expire. So the base is `persistent` with `keepLastSnapshots: { count: 1 }` and a bounded `snapshotExpiration` (never `0`), every fork and the Code sandbox are `persistent: false` (said again with `update` after `fork` and `getOrCreate`, because an existing Sandbox keeps its old settings), and every delete passes `deleteOrphanSnapshots: true`. The base's snapshot is never assumed to exist: a fork that fails twice deletes the base with its snapshots and rebuilds it once, and a third failure refuses the Run with "The Screen sandbox is unavailable". `sandbox-snapshots.test.ts` pins these options.
- **The harness talks to it by name.** `server/screen.ts` runs `curl` inside the sandbox against the driver's control port, with a per-Run secret the page never has. Any function instance (a workflow step, an MCP call) finds the sandbox by its name, `operator-screen-<run id>`.
- **Code runs in a second sandbox.** `run_code` gets its own microVM (`operator-code-<run id>`, no network) with the Task, the Manifest, what the Run has changed so far and a check-digit helper. If it shared the Screen sandbox, code the model wrote could post to HARBOURMASTER on loopback and skip the Guard. The keyboard is the only way in.
- **The same machine runs in three places**: the sandbox, the visitor's browser ("take the keyboard"), and the server's replay of a hand attempt. The checks therefore read the same `Books` whoever keyed.

## Consequences

- After changing anything under `legacy/`, `domain/guard.ts`, `domain/rule-kinds.ts`, `domain/iso6346.ts` or `server/sandbox/`, run `pnpm build:operator-screen`; `screen-bundle.test.ts` fails on a stale bundle. Keep those modules free of runtime imports beyond each other (no zod, no Node APIs in `legacy/`).
- Sandbox time is billed to the Vercel team. A Run's Screen sandbox lives at most `LIMITS.sandboxMinutes`; ending or stopping a Run deletes both sandboxes, and a Run that lost its workflow is closed by the stale sweep on the next read.
- Without Vercel credentials (no `VERCEL`, `VERCEL_OIDC_TOKEN` or `VERCEL_TOKEN`) no Run can start and the page says so; taking the keyboard, the recorded Run and the Rules still work.
- Frames are PNGs in the private `operator` bucket (`frames/<run id>/<n>.png`), served only through the gated Frame route. The Owner purge removes the rows; the pictures of purged Runs stay in the bucket until a sweep is written. They are synthetic terminal screens, but this is a known gap.
- A sandbox is created in the default region (`iad1`) while the functions run in `syd1`; each Action is one control-plane call, about half a second.
